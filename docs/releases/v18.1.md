# netscaler-quickcheck v18.1 (2026-11-05)

Status: gelaufen (Betreiber-Gateway 2026-11-05 07:41, Script 930cfc26...)

Validated on 14.1-73.49 in the lab and on a customer gateway between 2026-11-04 and 2026-11-05. Rules stand 2026-11-05d. Everything else as in `v18.0.md`.

## New in v18.1

- **Shared addresses (proxy, NAT, carrier).** An address with at least `AAA_SHARED_OK` successful logons (default 20) from at least `AAA_SHARED_USERS` accounts (default 10) in the window, and no machine behaviour, is a shared address: its failed attempts are reported as INFO with the counts ("900 successes on 60 accounts, 15 failed attempts on 5 accounts"), category `aaa_shared`, never in the share file or the feed. Account-based checks (brute force per account, success after a failure series, machine rate, spraying without success) still apply to such addresses. Background: cloud proxies such as Netskope or Zscaler put hundreds of users behind one egress address; their typos looked like sleepers, and trusting the address would also trust an attacker behind the same proxy.
- Category of trusted sleepers renamed to `trusted_aaa_sleeper` (was `trusted_aaa_schlaefer`); `trusted_aaa_unklar` and `trusted_aaa_maschine` unchanged.
- **Advice per address** under sleeper and spraying rows: successes of the address (count, accounts, names), the failing accounts that never succeeded from it, and a recommendation by situation: typos of own users (A), foreign attempt or stale saved password through a user's address (B), dictionary or leak spraying (C), foreign attempt on known accounts (D), a single account without success (E). Codes `AAA_ADV_*` in the catalogs; account names are mapped in anonymized copies.
- **nFactor.** A `LOGIN_FAILED` within 120 seconds after a passed first factor of the same account (`AAA_FACTOR_OK_RE`, the `AAATM ... Authentication succeeded, current factor: ...` line) counts as a user with a wrong password. Addresses whose failures are all explained this way are INFO (category `aaa_factor_ok`, advice F: AD password forgotten or password manager with a stale value); partly explained addresses carry "of these, n after a passed factor". The factor lines have severity DEBUG and reach the local `ns.log` only with `audit logLevel ALL`; with nFactor configured and no such lines the header says so. Fixture `nfactor`, test log `nfactor.log`.
- **Later success.** A success of the same account from the same address within `AAA_OK_WIN_LATE` (default 24 h) after the last failed attempt rates the address as a user who remembered or reset the password: INFO, category `aaa_late_user`, advice G, instead of sleeper or spraying. A success from another address does not count (an attacker failing while the user logs on elsewhere must stay yellow). Fixture `late`.
- **Rules 2026-11-05b.** `AAA_OK_RE` now matches `SSLVPN LOGIN <n> 0 : Context` with one or two spaces (14.1-73.49 on a customer gateway writes one, the lab two) and no longer matches the diagnostic line `"AAA LOGIN : X509 cert not found"`; before this, successes on that gateway were not counted at all. The removed alternative also matched `AAA LOGIN REQ` lines (login requests): since 17.28 a request following a failure within 5 minutes could pass as a success and rate the address as "user, no finding"; that false negative is closed. Same spacing fix in `AAA_FAIL_RE` and the factor patterns. Test log `aaa-ok-formats.log`.
- Fixes: `msg()` was called before the catalog was loaded (CLI user from the snapshot config, option error paths; "msg: not found"); `--anon` now reads pipes and `/dev/stdin`; accounts seen only in success lines are now in the mapping table (an account that never failed was left in clear text).
- **Hit vs. proxy.** The red "success after a failure series" needs machine rate or exactly one account that succeeded after the series: a sprayer finds one password, users behind a proxy find many. The number of distinct accounts alone no longer makes an address a machine when it meets the shared-address thresholds, and the /24 rule does not apply to such addresses. Found on a customer gateway where a cloud-proxy address with eleven accounts failing once and five succeeding afterwards was rated as a hit (FORENSICS_FIRST). Fixture `shared-hit` holds both: the proxy and a real sprayer.
- Account names are normalized for the evaluation (lower case, domain prefix removed); raw spellings go into the mapping table so they are masked in anonymized copies, including the dotted form in which non-ASCII characters appear in the report (an account such as `M..ller` stayed readable in a customer report).
- **Account files per run.** `<report>_accounts.tsv`: one row per account with failed attempts (failures, successes, addresses, first and last failure, first success after a failure, situation code A to G of its address). `<report>_logons.tsv`: the timeline, one row per event (account, raw spelling, time, address, result `fail`/`ok`/`factor_ok`/`factor_fail`, detail). `ns_quickcheck_observed_accounts.tsv`: cumulated per account over all runs (first and last day, days with events, failures, successes, max addresses per run, last situation); events are counted once even when windows overlap. A yellow finding names accounts with failures on at least `ACC_DAYS_MIN` days (default 3) and no success at all. All three with anonymized copies, mode 600, named in the footer.
- **Finding codes in the JSON, for real.** v18.0 announced and documented `code` per finding, but the script never emitted it (the key was recorded and not read). 18.1 emits `code` in `red`, `yellow`, `orange` and `trust`; the per-CVE entries carry `BUILD_VULN_JSON_PREFIX`. Collectors keying on `code` need 18.1.
- **Coverage against rotation.** In online mode the oldest file of `ns.log`, `messages` and `httpaccess` is compared with the window start; if the rotation does not reach back that far, `coverage=partial` with an INFO naming the reach, the file count and the days per rotation. Found on a customer gateway where 25 `messages` files covered four days of a 168 h window and an injection finding silently rotated away between two runs.
- **Comparison with the last run.** The newest JSON of the host in the report directory is read; red and yellow codes that are new or gone are listed in block 6 (gone with the previous text), `new=<n>` and `gone=<n>` in RESULT. Vanished findings keep their addresses in the cumulative list.
- **Session secrets.** `Session Key` from `show aaa session` is masked in the report itself; the anonymizer also masks `Session Key`, `NSC_*` and `SESSID` cookie values and counts them as secrets. A customer report carried a live session key in clear text.
- **Compact `[TRUST]` block.** One block with one line per trusted address (categories with counts, validity, remark) and the check paragraph once, instead of a block per address; `DETAIL_MAX` applies. The warning "in trusted_ips, but listed as an attacker" is one line naming all addresses and appears only in the first run in which the address is trusted (it repeated on every run before).
- **Shell activity (opt-in, `SHELL_CHECK=1`).** `/var/log/bash.log` (and `sh.log`) is read, interactive TTYs only (pts, console), because system scripts log every command there with account and TTY `(null)` and filled a customer report with 4,000 lines; command lists are capped by `SHELL_CMD_MAX` (50). With the block off, an INFO says how to enable it. Sessions per shell PID with account, TTY, start, end and the commands (INFO). sessions per shell PID with account, TTY, start, end and the commands in full (INFO). Yellow for a pts session without a logon in `auth.log` within `SHELL_LOGIN_WIN` minutes before (a shell without logon is the pattern of a webshell spawning `/bin/sh`; console sessions are exempt) and for sessions after a logon from outside. Red for commands matching `SHELL_SUSPECT_RE` (download with URL, `chmod +x`, `base64 -d`, `nohup`, interpreter `-e`, `crontab`, log deletion, writes into web directories, start from `/tmp`, `nc`/`socat`), with the logon address as `shell_source`; red without a logon or from outside counts as compromise. `shell_sessions=<n>` and `shell_suspect=<n>` in RESULT. The login correlation is by time only (the `bash.log` line has no address); the `auth.log` format of the lab is still to be confirmed. Rules 2026-11-05c, test log `shell.log`, fixture `shell`.
- **`AAA_FACTOR_LOG`.** A separate log file for the nFactor factor lines (for operators who route DEBUG to its own file); read in the window like the other logs.
- **Scanner payloads in CSP reports.** `AAA Message ... "CSP Violation: ..."` lines are the browser's Content-Security-Policy reports for the logon page; the `blocked-uri` field is client-controlled. A customer gateway received the Burp Scanner OS command injection probe there. These lines are now a finding of their own (red, "scanner pattern"), with the source taken from POSTs to the CSP report path (`CSP_REPORT_PATH_RE`) in the access log, category `csp_scanner`, and the advice to check for a commissioned pentest first; the gateway's own FQDN in the line is no longer taken as a download host. Rules 2026-11-05d, fixture `csp`.
- **Anonymization of public gateway names.** The FQDN under which users reach the gateway (from `accessing page https://<host>/` in CSP reports and `Hostname:` in responder lines) is now in the mapping table; it stood in clear text in anonymized copies.
- Log lines with `\n` in payloads are printed with `printf` instead of `echo` (the FreeBSD sh `echo` expands backslash sequences and split such lines).
- New fixture `shared`.
